# icx4 results: the first 4-class model on ImageCAS-X, read as pre-registered

**Question.** How good is icx4 (nnU-Net v2 ResEnc, 0.5 mm, 256³, 1000 epochs, ImageCAS-X 560/80 collapsed by D25) on
the decisive metric, and what does Round 9's pre-registered reading (A26, A27, A29, A15) say to do next?

**Setup.**
- **The model:** `trillium/icx4` on Fir (A25).
  - Training: epochs 0–999 over three chained jobs (23.2 h + 23.3 h + 7.7 h), about 192 s/epoch.
  - Then prediction of all 1000 cases, aortas for the 160 non-sealed val and open cases, and in-job tF1 on the
    open 80.
- **Decisive set:** val 80 (A26), scored by `experiments/Atlas/r9_score_icx4.py`. That scorer runs icx4's own
  in-job scoring code, with the in-job aortas and CT.
- **Metric:** tF1 @ 1.5 mm at A1c `24441cf8…5254`. Provisional cases and flagged trees are left out (A1a/A1b).
- **Other sets:** open-36 confirms; dev-44 is reported apart.
- **No sealed case is read.**
- **The reading** was run by the lead on Fir (16-core CPU job, 2026-10-23) with `experiments/Atlas/r10_read_icx4.py`,
  `r9_score_icx4.py` and Delta's `experiments/Delta/r9_fir/score_tf1.py`. Its full output is posted verbatim on #43.

**What #43 originally asked for, and what replaced it.** #43's acceptance criterion was "test-split (160 cases, never
trained on) per-class Dice". Round 9 superseded it:

- **A14/A26:** the 80 sealed test cases are never read before the final milestone, so only the 80 open test cases
  are scored.
- **A26:** val 80 decides, with tF1.
- **A28:** Dice decides nothing. It is reported, on the open 80, for comparison with the literature only.

This note reports what Round 9 asks for in its place.

## Checks on the reading (Atlas, 2026-10-24; details on #43)

1. **A26 was a real recomputation, not a cache read.**
   - `r9_score_icx4.py` reads only `sealed_test.json`, `splits.json` and `layout.json` as JSON. It recomputes every
     case from the prediction, label, aorta and CT through `tf1_score.score_case`.
   - The in-job cache (`$W/tf1.d/`) is used only by the in-job worker `tf1_score.one()`, which the scorer never
     calls.
   - **The apparent timing gap was a misreading.** `job_body.sh` stamps hours since job start, not stage durations,
     so the in-job tF1 stage took about 0.2 h (9.7 → 9.9), not 9.9 h. That is 2–3× slower per case than the
     16-core CPU job, which is consistent with 10 workers sharing a GPU job's 12 cores.
   - **An independent implementation agrees.** Delta's scorer is different code: an 8 mm crop and no CT. With the
     TotalSegmentator aortas it gives an all-trees val mean of 0.9169 − 0.0079 = **0.9090**, equal to the r9
     scorer's 0.909.
2. **0.909 is the decisive number. Delta's 0.917 is the P2 sensitivity number.**
   - The 0.0079 gap (0.9173 vs 0.9094 decisive; 0.9169 vs 0.9090 all trees) is exactly the expert-minus-
     TotalSegmentator ostium Δ that withdrew P2.
   - It sits entirely in the left tree (LM +0.010, LAD +0.011, LCx +0.011; RCA identical). A few val cases carry it:
     4.3 % of ostia are more than 2 mm from the expert start, and the CI's lower bound is 0. On open-36 it is 0.
   - With P2 withdrawn, A1 as written (the TotalSegmentator ostium) is the rule of record.
   - No A27 line is within 0.008 of the decisive numbers. The closest is LCx, 0.857 against 0.80.

## What it changes

**The recipe stands** (macro ≥ 0.85, A26 passed).
- icx4 is the base model for the pool reads. Fine-tunes enter through A17a/b as reads arrive, and every retrained
  decision follows A22.
- Before wave-1 fine-tuning, the `coronary_icx4` segtrain task config is due (A32).

**A27: whole-tree Dice on the open 80 < 88.3** (report only).
- The obligation: check preprocessing, the collapse and the window before the predictions are used (for example as
  pool seeds or for the A31 domain check).
- It is indicative, not paired: ImageCAS-X's Table 2 includes our sealed 80.
- The margin is small. 87.9 is 0.4 below the line, and Foxtrot's own CI half-width for this number is about ±0.7.
- **The check is `experiments/Atlas/r10_dice_check.py`** (CPU, report only; the commands are on #43). It tests
  F7.1's premise that the model "loses tree". The tF1 recall already argues against it: open-80 macro tF1 is
  0.912, with no class below 0.88. The check measures, per case:
  - the prediction's grid and label values (preprocessing);
  - binary centreline recall and precision (lost tree);
  - a 1-voxel-tolerant Dice and the volume ratio (lumen width);
  - the CT HU of missed, extra and shared voxels (window).

  The **collapse cannot move a whole-tree Dice** (it is binary, and D25 only renames voxels). The script confirms
  that the reference union is unchanged.

  **Result (run by the lead on Fir, 2026-10-24; below): lumen width.** The obligation is discharged.

**A27/A15: FP per case ≤ 1.**
- A15 is met on val, and A24's FP-loss line is closed.
- The FP gate stays an acceptance criterion on the final model (A15).
- The census's softmax question is moot: the census was only required if FP > 1. Its no-softmax run counted 29
  components, a median 3.0 mm from the tree.

**A29: P2 withdrawn.** TotalSegmentator aortas stay required for every decisive score (A1 as written).

**Reading (Atlas, agreeing with the PM):**

| F7.1 cause | Evidence | Verdict |
|---|---|---|
| Preprocessing | grids and values clean in all 160 | ruled out |
| Collapse (D25) | the reference union is unchanged; whole-tree Dice is binary anyway | ruled out |
| Lost tree (F7.1's premise) | centreline recall 0.94–0.97, precision 0.95 | ruled out |
| **Lumen width** | 1-voxel-tolerant Dice 0.97 against plain 0.88; predicted volume about 13–14 % below ImageCAS-X's | **the cause** |
| Window | missed voxels about 237 HU against 372 HU in the overlap. That is the dim partial-volume rim, inside nnU-Net's default normalisation range (foreground 0.5–99.5 percentiles, about 61–808 HU on this dataset), so nothing is clipped. The model's extra voxels are just as dim (about 240 HU) | a boundary convention on a dim edge, not a window artefact |

The model places the lumen boundary about one voxel inside ImageCAS-X's, on net. On 2–8-voxel lumens, that costs
Dice much and tF1 almost nothing.

**What it changes:**
- **No decision changes** (tF1 decides; A28).
- **The predictions are usable as they are.**
- **The A31 pre-read domain check:** report the 1-voxel-tolerant Dice and the volume ratio beside plain Dice. Then a
  uniform width difference is not read as domain shift. `r10_dice_check.measure()` computes both.
- **Seeds:** under D23/D26 the pool seeds are TotalSegmentator's, so nothing changes today. If an icx4-family model
  is ever used as a prelabel, expect annotators to widen rims by about one voxel (allowed, D12).
- **Lumen width** would matter only for a calibre-based use (e.g. stenosis), which is not in scope. No lever is
  proposed.
