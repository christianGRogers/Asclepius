## 1. Verdict in five lines

1. **The rotation dispute does dissolve as a dispute — and the ablation gets *more* justified, not less.** The two papers measure different operations, as the vault says, but the reason is stronger than the vault found: ImageCAS's 90°/180°/270° rotations are exact axis permutations requiring **no interpolation at all**, while nnU-Net's ±30° resamples the label through a trilinear one-hot + argmax that systematically thins a 3-voxel tube. nnU-Net's version carries a second, unbounded harm that ImageCAS's did not. Keep the ablation; fix the plan's citation; run the free label-retention check first, which may close it on paper.
2. **§1.6 is right that mirroring bites twice but wrong that there are two switches.** `mirror_axes` is not in the plans JSON; it is derived at runtime from patch shape and persisted in the **checkpoint**. There is one decision point — the trainer class — and `--disable_tta` is not it. The repo's `nnUNetTrainer_segtrain` does not override it, so mirroring is live in training *and* in TTA today. For the binary tasks that is defensible; for multiclass it is the silent correctness bug the prompt suspected, and nothing in `configs/` can express the ban.
3. **The lumen-only normalisation window is a genuine mechanism with the vault's expected direction probably backwards.** Confirmed in source. But ImageCAS's masks include plaque and veins, which *widens* 710's window, while ImageCAS-X's clean lumen *narrows* 711's — and 711 is the model that seeds annotation. The gate must read four fields and three derived thresholds, and the counterfactual is a `plans.json` edit, not a code change.
4. **Both anisotropy gates are formalities on this cohort, and the repo's `max_spacing_mm` guard is not a guard.** ImageCAS is documented at planar 0.29–0.43 mm and spacing 0.25–0.45 mm: worst in-case ratio ≈1.55 against `ANISO_THRESHOLD = 3`. Neither the spacing branch nor the separate-z branch can fire. `max_spacing_mm: 0.5` prints a warning from `describe_plans` and nothing else; `docs/TRAINING-PHASE1.md:155` claims it "refuses that outright", which is false. The one anisotropy branch that *can* fire on this cohort is the one nobody named: `do_dummy_2d_data_aug`, keyed on **patch aspect ratio**, not spacing.
5. **TTA is a non-question, and the vault reached the right answer through arithmetic that is wrong by an order of magnitude and a cost/benefit table that is backwards.** nnU-Net's TTA *is* mirroring, 8 forward passes, nothing else. Ban mirroring and there is no TTA to schedule. Where it does apply (binary), it costs ~2 GPU-hours over 250 cases, not 40–125. And `tile_step_size` is a pure inference argument — raising overlap needs no retraining, contrary to the note.

## 2. Errors found, ranked by what they change

### E1. The elastic-deformation note describes a transform that nnU-Net v2 does not apply. Removes an experiment.

- **Vault says:** `Elastic and spatial augmentation for thin tubular structures.md:41–49` — "nnU-Net v2 applies elastic deformation with `alpha = (0, 900)` (voxel units) and `sigma = (9, 13)`… Elastic deformation is applied with probability ~0.2 (20 % of patches)", "nnU-Net's planner automatically scales these to match the patch and spacing; effective α becomes order ~20–50 voxels." Recommendation 1 (`:99`) is "**Keep elastic deformation in the baseline** — it is nnU-Net's default". `Proposed changes to the training plan.md:352` schedules an "elastic-deformation ablation" as conditional experiment 6.
- **Actually true:** elastic deformation is **off** in nnU-Net v2. `nnunetv2/training/nnUNetTrainer/nnUNetTrainer.py:761` (v2.8.1) constructs `SpatialTransform(..., p_elastic_deform=0, p_rotation=0.2, rotation=rotation_for_DA, p_scaling=0.2, scaling=(0.7, 1.4), ...)`. Every DA variant trainer in the repo (`nnUNetTrainerDAOrd0.py:53`, `nnUNetTrainerNoMirroring.py:86`) repeats `p_elastic_deform=0`. `batchgeneratorsv2 v0.3.5` `transforms/spatial/spatial.py:21–24` shows the library's own default is also `p_elastic_deform=0`, with `elastic_deform_scale=(0, 0.2)` and `elastic_deform_magnitude=(0, 0.2)` — there is no `alpha`/`sigma` parameter pair in v2 at all. `alpha=(0., 900.)`, `sigma=(9., 13.)`, `p_eldef=0.2` are nnU-Net **v1** `default_3D_augmentation_params` — and v1's `nnUNetTrainerV2` set `do_elastic = False` as well. The "planner automatically scales these" claim has no referent in either version.
- **Fix:** delete recommendation 1, 3 and 4 of that note and the §3.4 priority-6 "elastic-deformation ablation". There is nothing to ablate. The note's only surviving content is the scaling range, and even that is misquoted (`:82` says 0.7–1.3; nnU-Net passes 0.7–1.4 — 0.7–1.3 is the *library* default, not nnU-Net's).
- **Also in that note:** `:27` attributes DS6 (*Deformation-aware Semi-supervised Learning: Application to Small Vessel Segmentation with Noisy Training Data*, PMC9605070) to "Chlebus et al." DS6 is Chatterjee et al. (J. Imaging 2022). I could not re-verify this session (search quota), so treat as **probable misattribution, one check needed** — but the note's own admission that "no direct ablation of elastic vs non-elastic is given" means nothing rests on it.

### E2. §1.6's framing invents a second switch and misses the one that exists. Changes how the ban gets enforced.

- **Vault says:** `Proposed changes to the training plan.md:155–159` — "Mirroring is disabled in two places, and the plan names one… Both need disabling." Marked **[reported]**. The prompt asks which of `--disable_tta` / `mirror_axes` / `inference_allowed_mirroring_axes` in the plans JSON controls what.
- **Actually true:** there is **one** decision point, and it is neither the plans JSON nor `--disable_tta`.
  - `mirror_axes` does **not** appear anywhere in `nnunetv2/experiment_planning/` (`grep -rn mirror` → no hits). It is not a plans field and cannot be set in `configs/`.
  - It is computed at runtime in `nnUNetTrainer.configure_rotation_dummyDA_mirroring_and_inital_patch_size` (`nnUNetTrainer.py:472–513`). For `dim == 3` the assignment is **unconditional**: `mirror_axes = (0, 1, 2)` at line 496, outside the `do_dummy_2d_data_aug` branch. Line 511: `self.inference_allowed_mirroring_axes = mirror_axes`.
  - It is persisted in the **checkpoint**: `nnUNetTrainer.py:1214` writes `'inference_allowed_mirroring_axes': self.inference_allowed_mirroring_axes`.
  - Inference reads it from there: `predict_from_raw_data.py:92–93` then `:137`; the actual use is `:575` `mirror_axes = self.allowed_mirroring_axes if self.use_mirroring else None`.
  - `--disable_tta` sets `use_mirroring=False` (`:833`, `:894`) — it suppresses *inference* mirroring only and does nothing about training-time mirroring. It is a performance flag, not the ban.
  - A third site the vault misses entirely: the trainer's own end-of-training validation, `nnUNetTrainer.py:1272–1277`, builds `nnUNetPredictor(tile_step_size=0.5, use_gaussian=True, use_mirroring=True, ...)` and hands it `self.inference_allowed_mirroring_axes`. So the `validation/` folder nnU-Net writes — the numbers anyone will quote — is 8× mirror-averaged too.
- **What must be set:** override `configure_rotation_dummyDA_mirroring_and_inital_patch_size` to set both the return value and `self.inference_allowed_mirroring_axes` to `None`, exactly as `nnUNetTrainerNoMirroring.py:30–35` does. That single override disables all three sites. Nothing else works, and `MirrorTransform` is only appended `if mirror_axes is not None and len(mirror_axes) > 0` (`nnUNetTrainer.py:831`), so `None` is sufficient.
- **One trap the vault does not name:** `nnUNetTrainer.load_checkpoint` (`:1239–1240`) *restores* `inference_allowed_mirroring_axes` from the checkpoint, overwriting whatever `configure_…` set. For the repo's chained-resume design (`SEGTRAIN_MAX_SECONDS` → `--c`, `chain_max: 3`) this is consistent as long as the trainer class never changes mid-chain. If a run is ever resumed or fine-tuned under a different trainer than the one that wrote the checkpoint, the axes come back. Worth one assertion.
- **Fix to §1.6:** rewrite as "mirroring is decided once, in the trainer, and takes effect in three places (training transform, nnU-Net's own validation, `segtrain evaluate`). `--disable_tta` is not the control and the plans JSON has no field for it." Upgrade the marker from **[reported]** to **[source]**.

### E3. The repo has the mirroring bug the proposals predict, and no config can express the ban.

- `src/segtrain/nnunet_ext/nnUNetTrainer_segtrain.py` — read in full — overrides `__init__`, `on_train_start`, `on_epoch_end`, `save_checkpoint`, `on_train_end`, `run_training` and adds `_pause`. It does **not** override `configure_rotation_dummyDA_mirroring_and_inital_patch_size`. Its own docstring (`:4–6`) says "the loss, optimizer, schedule and augmentation are untouched nnU-Net defaults". So every run gets `mirror_axes = (0, 1, 2)`.
- `src/segtrain/evaluate.py:51–61` constructs `nnUNetPredictor(tile_step_size=0.5, use_gaussian=True, use_mirroring=True, ...)` with the comment "Mirroring IS enabled here: this is the final number and nnU-Net's default inference includes test-time augmentation." That is correct today for 710/711 and becomes wrong the moment a multiclass checkpoint is evaluated with a trainer that did not null the axes.
- `configs/tasks/Dataset710_CoronaryLumen.yaml` and `Dataset711_CoronaryLumenX.yaml` have no augmentation or mirroring key at all; `src/segtrain/config.py` `TaskConfig` has no field for one (`:437–466`). So the plan's §4 ban is unenforceable by configuration — it requires either a second trainer class or a task-level flag that selects one.
- **Status for phase 1:** not a bug. Both phase-1 tasks are single-foreground-class (`configs/labels/coronary_lumen.yaml`, `count: 1`), so mirroring cannot corrupt labels. It is a bug the day a multiclass task exists, and the gate proposed in the mirroring note (`:108–110`) — assert the trainer logs `mirror_axes = None` for a multiclass task — is the right shape. Note the trainer does *not* currently log `mirror_axes`; it logs only `do_dummy_2d_data_aug` (`nnUNetTrainer.py:510`). The gate needs either a log line added or the checkpoint field read back.
- **Stale reference:** the mirroring note `:94–96` cites `src/segtrain/preview.py` setting `use_mirroring=False`. That file no longer exists (`ls src/segtrain/` — removed in `27b2b13`, "Remove the Slicer monitor and what only existed to feed it"). The bullet and its caveat about previews differing from final numbers should be deleted.

### E4. `max_spacing_mm` is a printed warning, not a guard, and the failure it guards against cannot happen.

- **Vault/repo says:** `configs/tasks/Dataset710_CoronaryLumen.yaml:46` "Refuse a planned target coarser than this"; `docs/TRAINING-PHASE1.md:155` "`max_spacing_mm: 0.5` in the task config **refuses that outright**"; `src/segtrain/plans.py:14–16` and `:253–266` describe it as closing the hole native leaves.
- **Actually true, mechanism:** `spacing_warnings()` (`plans.py:253–283`) returns a list of strings. Its only caller is `describe_plans()` (`plans.py:248`), which appends them as `WARNING` lines to a human-readable summary. `grep -rn "spacing_warnings\|max_spacing_mm"` over the repo finds no other call site — not in `cli.py`, not in `slurm.py`, not in `backends/`. Nothing raises, nothing exits non-zero, and `segtrain scinet submit` does not consult it. It also does not exclude anything: the docstring's own remedy is manual ("Either drop them, or set an explicit `spacing:`"). So the answer to the prompt's question is neither of the two options offered — it does not exclude cases from the median *or* from training; it prints a line a human may read.
- **Actually true, quantitatively:** the failure is near-impossible anyway. `determine_fullres_target_spacing` (`default_experiment_planner.py:155–196`) takes `np.percentile(spacings, 50, 0)` — a per-axis **median** over ~1000 cases. A median does not move for a handful of outliers; it takes roughly half the cohort to shift it. And ImageCAS's documented spacing is verbatim: *"The images have sizes of 512×512×(206-275) voxels, a planar resolution of 0.29-0.43 mm², and spacing of 0.25-0.45 mm"* (arXiv:2211.01607v2, §3). To plan a 0.5 mm target you would need most of the cohort above 0.5 mm, which contradicts the dataset description. Dataset711 is a subset of the same scans, so the same holds.
- **Fix:** keep the check — it costs nothing and a documented range can be wrong — but reclassify it honestly. Change the docs and the config comment from "refuses" to "warns", and either (a) make it fail (`raise` in the `plan` command when a hard floor is violated) so the word matches the behaviour, or (b) say it is a tripwire on the dataset description, not a guard on a live risk. Today the docs promise a safety property the code does not provide, which is worse than having no guard.

### E5. Three anisotropy branches are conflated into one gate, and the one that can actually fire is unnamed.

- **Vault says:** `Proposed changes to the training plan.md:300` — gate "Confirm the anisotropy branch does **not** fire / If it does, through-plane resampling silently drops to nearest-neighbour for image and label", **[reported]**, to be read "from the planner printout" (§3.1 preamble, `:294`, and the resampling note `:92–99`).
- **The nearest-neighbour half is correct and now [source]:** `default_experiment_planner.py:113–135` `determine_resampling` returns, for data, `{"is_seg": False, "order": 3, "order_z": 0, "force_separate_z": None}` and for seg `{"is_seg": True, "order": 1, "order_z": 0, "force_separate_z": None}`. `order_z = 0` for both. `resample_data_or_seg` docstring (`default_resampling.py:117`): "separate_z=True will resample with order 0 along z". So yes — image and label both drop to nearest-neighbour through-plane. Vault claim confirmed verbatim.
- **But there are three distinct branches with three triggers and three observables, and the gate names one ambiguously:**
  - **(A) Target-spacing branch** — `determine_fullres_target_spacing:186–195`. Fires only if `has_aniso_spacing` **and** `has_aniso_voxels`, both at threshold 3. Observable: the planned `spacing` in the plans JSON (it would use the 10th percentile of the worst axis). Cannot fire here (ratio ≈1.55).
  - **(B) Separate-z resampling** — `determine_do_sep_z_and_axis:33–66`. Fires **per case**, on `get_do_separate_z(current_spacing)` *or* `get_do_separate_z(new_spacing)`, `max/min > 3`. This is not a dataset-level property and is **not visible in the plans JSON at all**. One 3 mm-slice case in the cohort would be resampled to 0.35 mm z by slice replication and train as if it were fine-resolution — silently. Observable: only by computing max/min per row of `dataset_fingerprint.json["spacings"]`. Cannot fire on ImageCAS as documented, but this is the check the gate should actually be.
  - **(C) `do_dummy_2d_data_aug`** — `nnUNetTrainer.py:490`, `max(patch_size) / patch_size[0] > ANISO_THRESHOLD`. **Keyed on patch shape, not spacing.** A near-isotropic dataset can trip this purely because the planner produced a flat patch. If it fires, rotation becomes **±180°** (`:493`) instead of ±30°, a `Convert3DTo2DTransform` is inserted (`:752–755`), and `SimulateLowResolutionTransform` gets `ignore_axes=(0,)`. That is a large, invisible change to the augmentation regime — and given the plan's §5 anxiety about rotation, it is the branch that matters most here. Observable: the trainer logs it, `nnUNetTrainer.py:512` `print_to_log_file(f'do_dummy_2d_data_aug: {do_dummy_2d_data_aug}')`. It is **not** in the planner printout.
- **Fix to §3.1 row 2:** replace one row with three. (i) planner: assert planned spacing is native and `max(patch_size)/patch_size[0] ≤ 3`; (ii) fingerprint: assert `max(s)/min(s) ≤ 3` for **every** case in `dataset_fingerprint.json["spacings"]`, and report the worst case's id; (iii) trainer log: assert `do_dummy_2d_data_aug: False`. Only (i) is readable from the planner printout the gate currently points at. `src/segtrain/plans.py:describe_plans` already prints spacing and patch size and is the natural place for (i) and (ii).

### E6. The −12.32 % resolution penalty was measured with nearest-neighbour downsampling. Weakens §1's headline evidence.

- **Vault says:** `Proposed changes to the training plan.md:163–167` — "The ImageCAS resolution penalty is **−12.32 %** (512²×256 → 128³, p < 0.0001). Worth adding the intermediate point, **−7.38 % at 256²×128**". Plan §1 (`Training plan.md:38–41`) rests on it: "ImageCAS measured the cost directly: −12.3 % Dice going from 512²×256 to 128³ input, six times the effect of any architectural change they tried."
- **Both numbers confirmed verbatim** (arXiv:2211.01607v2, §5.2.1): *"the input size of 512 × 512 × 256 significantly improves the Dice score by 7.38% (p<0.0001) and 12.32% (p<0.0001) compared to that of 256 × 256 × 128 and 128 × 128 × 128, respectively."*
- **New caveat from the same sentence's predecessor:** *"Input size including 128 × 128 × 128, 256 × 256 × 128, and 512 × 512 × 256 are discussed which are obtained by **nearest neighbour interpolation** of the original image."* The downsized inputs were produced with the worst possible kernel for a 3-voxel tube — the very choice the resampling note argues against. The measurement therefore conflates *resolution loss* with *bad interpolation*, and it is an **upper bound** on the cost of resolution loss under a proper resampler (nnU-Net uses order-3 for the image and one-hot-threshold for labels).
- **Why it matters:** this number is the plan's single strongest quantitative argument for "no cascade, no coarsening". The direction is surely right and the conclusion survives — a cascade's low-res stage still destroys distal branches — but the plan should stop quoting 12.32 % as *the* cost of downsampling and say "up to −12.3 %, measured with nearest-neighbour downsampling on a non-nnU-Net pipeline; the penalty under nnU-Net's own resampler is unmeasured." Same discipline the proposals already applied to the 82.96 % benchmark in §1.4.

### E7. The TTA note's cost model, its cost/benefit table, and its recommendation are all wrong. See §5 below for the corrected arithmetic.

- **Vault says:** `Test-time augmentation for vessel segmentation and its inference cost.md:29` — "With 50 % patch overlap (order ~100–150 patches per volume)"; `:30` "TTA 3×: 150–450 seconds per volume"; `:32` "40–125 GPU-hours for inference-only"; `:77–78` higher overlap "Cost: ~1.5–2× single-pass time… Drawback: **must re-run from checkpoint; cannot be applied post-hoc**"; `:82` TTA "can be applied to any existing checkpoint; no retraining"; `:92` "Apply TTA with 3 augmentations: original, 10% scaling up, 10% scaling down"; `:97` "increase patch overlap to 90 % … and **retrain** from the best-validation checkpoint".
- **Actually true:**
  - **100–150 windows is the count for a ~128³ patch, i.e. nnU-Net's default 8 GB plan — not this plan's.** `compute_steps_for_sliding_window` (`sliding_window_prediction.py:30–54`): `num_steps = ceil((image - patch) / (patch·step)) + 1`. With the plan's ~256³ patch on a 512×512×~240 volume at `tile_step_size=0.5`: in-plane `ceil(256/128)+1 = 3`, through-plane 1 (the axis is shorter than the patch and gets padded). **9 windows**, not 100–150. The note silently used the patch size the plan spent 70 GB to avoid.
  - **TTA is 8×, not 3×, and it is mirroring only.** `predict_from_raw_data.py:574–590` `_internal_maybe_mirror_and_predict`: `axes_combinations = [c for i in range(len(mirror_axes)) for c in itertools.combinations(mirror_axes, i + 1)]`, then one forward pass per combination plus the identity, divided by `len(axes_combinations) + 1`. For `(0,1,2)` that is 7 + 1 = **8**. There is no scaling TTA, no rotation TTA, and no hook for one anywhere in `nnUNetPredictor`. The note's recommended experiment (`:92`, scaling variants only) is not something nnU-Net can do — it would require writing a custom predictor.
  - **Overlap is a pure inference argument.** `tile_step_size` is a constructor parameter of `nnUNetPredictor` (`predict_from_raw_data.py:44` region, and `src/segtrain/evaluate.py:52` passes `0.5`). Changing it requires no retraining and no new checkpoint. The note has the two columns exactly inverted: overlap is the post-hoc knob; TTA is the one fixed at training time, because the axes are baked into the checkpoint by the trainer.
  - **90 % overlap is ~13×, not 1.5–2×.** `tile_step_size=0.1` on the same volume: `ceil(256/25.6)+1 = 11` per in-plane axis × 1 = **121 windows** against 9.
- **Fix:** the note's conclusion ("do not schedule TTA") survives, but for the opposite reason and with the opposite cost ranking. Rewrite per §5 below. In §3.4 priority 6, **split "TTA / overlap tuning" into two items**: overlap tuning is a free post-hoc inference sweep worth doing once; TTA is not an available lever for the multiclass model at all.

## 3. Weak reasoning and unsupported leaps

### (1) The rotation dispute: the right conclusion, reached without the strongest argument — and that argument reverses the recommendation's rationale

The rotation note's five properties (`:40–65`) are all verified true, and its conclusion — "both can be true; nothing tells us what ±30° alone does" — is correct. But it misses the mechanism that actually separates the two experiments, and that mechanism is what decides whether the ablation is worth running.

**A 90°/180°/270° rotation is an exact axis permutation. It resamples nothing.** Every voxel maps to a voxel; no interpolation kernel is applied; the label is bit-identical up to relabelled coordinates. So ImageCAS's 2.63 %/2.73 % penalty is a **pure orientation-realism effect**, uncontaminated by any loss of detail. Their own explanation is exactly that ("coronary arteries have its own directions with corresponding surround anatomies… may produce unrealistic augmented samples").

**nnU-Net's ±30° rotation resamples both image and label onto an off-lattice grid.** From batchgeneratorsv2 v0.3.5 `spatial.py`: the image goes through `grid_sample` with `mode_image='bilinear'` (`:35`) — trilinear, note, *not* the order-3 used in preprocessing. The label goes through `_apply_to_segmentation` (`:275–368`); nnU-Net passes `bg_style_seg_sampling=False` (`nnUNetTrainer.py:764`), so the `else` branch runs: each present label is one-hotted, trilinearly grid-sampled, and the winner taken by per-voxel argmax (`:334–362`). That is a sensible, partial-volume-aware scheme — no integer-label interpolation bug — **but it is still a 0.5-effective-threshold on a trilinear one-hot at an off-lattice grid.** For a cylinder 3–6 voxels across, nearly every label voxel is a boundary voxel, so a rotation systematically erodes the label. Nothing in either paper bounds that erosion.

So the two harms are **additive in nnU-Net's version and absent-then-present across the two experiments**: ImageCAS measured harm-from-implausible-orientation with zero interpolation cost; nnU-Net's default carries a smaller orientation harm (±30° is plausible patient/cardiac-axis variation) *plus* an interpolation harm that ImageCAS's operation did not have and that falls hardest on exactly the structures this project exists to find.

**Verdict on the prompt's question:** the *dispute* dissolves — there is no contradiction, and the plan's §5 framing ("The two papers flatly disagree on this anatomy") is simply wrong and should be deleted. But the *experiment* is better justified after inspection than before, because inspection surfaced a second harm nobody had costed. It does not come off the list.

**The right experiment**, and it is cheaper than the plan implies:
- 2×2 on the **binary** model, fold 0: {rotation on/off} × {mirroring on/off}. Three new arms if the default run already exists. The rotation note's arm list (`:117–118` of the mirroring note) already says this; adopt it.
- **Do not run 90° rotations.** Correct, and for a sharper reason than the note gives: they are interpolation-free, so a 90° result tells you nothing about the interpolation half of the question, which is the half that is actually unknown.
- **What settles it:** rotation-off beating rotation-on by more than the fold-0 seed-to-seed spread, measured on **per-class branch detection rate and clDice on the smallest structures**, not mean binary Dice. ImageCAS's 2.7 % was mean Dice on a merged mask from a pipeline with far more variance; a 2.7 % effect would be detectable on 250 test cases, a 0.5 % effect would not. **Write the detectable effect size down before running**, the same discipline §3.4 demands of the ResEnc run.
- **Run the free half first** (see §4/(1)): the interpolation harm is measurable with no GPU at all.

### (2) The lumen-only normalisation window: genuine mechanism, expected direction probably backwards

Every step of the mechanism is confirmed:
- `src/segtrain/convert.py` writes `"channel_names": {"0": "CT"}` → `CTNormalization`.
- `fingerprint_extractor.py:59`: `foreground_mask = segmentation[0] > 0`. Foreground is the lumen, full stop.
- `:73`/`:179`: percentiles (0.5, 50, 99.5) over the pooled foreground samples.
- `default_normalization_schemes.py:61–73`: `np.clip(image, percentile_00_5, percentile_99_5)`, then `-= mean`, `/= std` — all three statistics from the lumen, applied to **every voxel of every image**.
- `default_preprocessor.py:79–88`: *"normalization MUST happen before resampling"*. Confirmed.

So the vault is right that this is real and unexamined. Two corrections to its reasoning, and they cut opposite ways:

**(a) For Dataset710 the window is probably wider than feared, and for Dataset711 narrower — which inverts the priority.** The proposals themselves establish (§1.5, **[verified]**) that ImageCAS's masks *include plaque, pulmonary vessels and coronary veins*. Plaque inside the foreground mask pushes `percentile_99_5` **up**, plausibly into the 800–1500 HU range; veins and generous partial-volume edges push `percentile_00_5` **down**. ImageCAS-X's clean lumen-only annotation does the reverse: a tighter mask gives a tighter window. So the narrow-window risk lands hardest on **711 — the model whose predictions become the annotation seeds** — and least on 710. Nothing in the vault notices this, and it reverses which run to check first.

**(b) The "loses look-alike context" argument (`:40–45`) is the weaker half, and it partly self-refutes.** The look-alikes that actually get confused with coronaries in CCTA are *other contrast-filled vessels* — pulmonary veins, coronary veins, the aortic root — all of which sit **inside** the window, where clipping does nothing. What clipping destroys is the distinction among *non-contrast* tissues below the lower bound: if `percentile_00_5` lands at, say, 150 HU, then lung (−900), fat (−100) and myocardium (+40) all collapse to one value and the heart's own outline disappears, which does undercut §2's stated reason for keeping whole volumes. If it lands near 0–50 HU — plausible, because a merged mask's partial-volume edge voxels reach well down into soft tissue — myocardium survives and only fat and lung collapse, which costs much less. The severity is entirely a function of one number, and the note is right that the number is free to obtain.

**(c) The upper bound is the sharper concern and the note states it correctly.** Calcium above `percentile_99_5` saturates to the same value as the brightest lumen. That is precisely the wrong compression for the one failure mode with the best physical characterisation. But see §4/(3): it matters through *continuity*, not boundary accuracy.

**Verdict: genuine risk, severity unquantified, direction of concern partly misassigned. Not a misreading.**

**What the pre-submission gate should read**, precisely. From `nnUNet_preprocessed/<Dataset>/dataset_fingerprint.json`, key `foreground_intensity_properties_per_channel["0"]`: `percentile_00_5`, `percentile_99_5`, `mean`, `std`, and also `median`, `min`, `max`. (The same dict is copied into the plans file — `plans_handler.py:321–325` `foreground_intensity_properties_per_channel` reads it from `self.plans` — which is why the counterfactual is a plans edit, not a code change.) Also read `median_relative_size_after_cropping`, because `determine_normalization_scheme_and_whether_mask_is_used_for_norm` (`default_experiment_planner.py:205–209`) branches on it at 3/4, and on a CCTA with no zero border it should be ≈1.0, giving `use_mask_for_norm = False`; anything below 0.75 means `crop_to_nonzero` did something unexpected.

Then assert three derived things, and print them for **710 and 711 side by side**:
1. `percentile_00_5 ≤ ~0 HU` — so myocardium and fat remain distinguishable rather than collapsing with lung and air.
2. `percentile_99_5 ≥ ~800 HU` — so dense calcium is not saturated into the lumen's brightest values.
3. `(percentile_99_5 − percentile_00_5) / std ≥ ~6` — the post-clip dynamic range in σ units, so the normalised image is not effectively two-valued.
A large 710-vs-711 difference is direct evidence that the **label definition**, not the images, set the intensity window — which is worth knowing regardless of whether any threshold trips.

Only if a threshold trips is the paired experiment worth a GPU block, and it is cheap: override `foreground_intensity_properties_per_channel` in the plans JSON with percentiles computed over whole volumes, or with a fixed clinical window. No fork, no code.

### (3) The cross-site note is the strongest note in the slice, and its correlates are the right ones — with one addition

`Generalising across scanners…md` earns its "solid" status. Two things it gets right that are easy to get wrong: the ASOCA→GeoCAD gap concentrating in **low**-calcification cases (`:29–36`), which is a genuinely counter-intuitive finding and correctly used to separate the calcium question from the cross-site question; and its refusal to import the +7.85 Dice appearance-augmentation number from a whole-heart preprint into a coronary decision (`:99–104`).

On the prompt's question — are contrast enhancement and edge sharpness the right correlates? **Yes, and for the right reason**: both are acquisition/reconstruction properties rather than patient properties, so they are the ones that shift when the scanner or protocol changes. I could not re-verify Zhang et al.'s coefficients (r = 0.408 / 0.239 / 0.201) this session (quota) — they remain **[reported]**, and the note itself correctly warns that a 40/70-case pair gives noisy correlations. One addition the note should make: report **voxel spacing and reconstruction kernel** alongside, because those are directly measurable from DICOM without any image analysis, and the kernel is the variable the confounders note separately shows changes blooming magnitude (0.93 sharp vs 1.07 soft). Enhancement and sharpness need computing; spacing and kernel are free metadata.

On whether the augmentation pipeline should change for a single-centre cohort: **not for the plan of record, yes for anything deployed.** The note's observation (`CT normalisation…md:126–129`) that nnU-Net's brightness/contrast range of ±25 % is narrower than the real protocol spread (258 → 653 HU, +153 %) is correct and well argued. But widening it now would (i) add a variable before a baseline exists, exactly what the plan's §3 sequencing rule forbids, and (ii) be untestable, because there is no second cohort in scope for phase 1. The right move is the one the note already makes: record it as a deployment decision with its evidence attached, and attach it to the ASOCA external validation in §3.3 rather than to the training config. If and when ASOCA is scored and the drop exceeds the predicted 5–8 points, *then* widening intensity augmentation becomes the first thing to try, and the note has already done the work of naming the two cheapest mechanisms.

### (4) The resampling note's central claim is asserted from mechanism and is now partly verifiable

`Resampling…md:23–28` describes `resize_segmentation` as per-class binary indicator interpolation plus threshold, and calls it partial-volume-aware. `default_resampling.py:130–131` confirms the routing (`resize_fn = resize_segmentation` for `is_seg`), and the equivalent augmentation-time scheme is now fully read (batchgeneratorsv2 `spatial.py:302–362`). So the mechanism claim is sound in both places. Its honesty about the gap ("asserted from the mechanism, not measured on our anatomy", `:57–58`) is exactly right and should be preserved. Its recommendation 1 ("no change needed to §1") is correct.

But its recommendation 3 — a resampling-scheme comparison as a future ablation — is the wrong experiment to have named, for a reason it could not see: on this cohort **nothing resamples**. Target spacing comes out at the per-axis median of a 0.25–0.45 mm cohort, so each case is resampled by a factor within ~±25 % of 1.0, and cases at the median are resampled not at all. The interpolation kernel barely matters at preprocessing. Where it *does* matter is **augmentation**, where every rotated patch resamples the label on an off-lattice grid at ±30°. The note has the right concern pointed at the wrong stage. See §4/(1).

### (5) "Not in dispute and stay" is doing real work as an unexamined assumption

`Training plan.md:120–121` — "Intensity augmentations (noise, blur, brightness, contrast, gamma, low-res simulation) are not in dispute and stay." The CT-normalisation note's recommendation 3 (`:145–148`) correctly says to record these as decisions with reasons. Worth adding the sharper point: they are "not in dispute" only because **nobody measured them separately either**. ImageCAS's ablation covered rotation, flip, patch size and the Frangi channel — not gamma, not blur, not low-res simulation. nnU-Net's evidence is the all-or-nothing augmentation variant. So the correct statement is "undisputed because unmeasured", which is a different epistemic status from "measured and kept", and the plan currently reads as the latter. The one intensity transform with a mechanism argument behind it is `SimulateLowResolutionTransform`, and the note makes that argument well (`:122–125`).

## 4. What's missing — extensions that would change a decision

### (1) Nobody has asked what nnU-Net's augmentation does to the *label* of a 3-voxel branch — and it is answerable for free, before any GPU time

This is the largest gap in the slice. The vault audits the preprocessing label resampler carefully and never looks at the augmentation-time one, even though the latter runs on ~20 % of every patch, every epoch, for 1000 epochs.

The experiment costs no GPU and no training:

> Take 50 ImageCAS-X label volumes. Instantiate `batchgeneratorsv2.transforms.spatial.spatial.SpatialTransform` with exactly the arguments `nnUNetTrainer.get_training_transforms` passes (`patch_size`, `patch_center_dist_from_border=0`, `random_crop=False`, `p_elastic_deform=0`, `p_rotation=1.0`, `rotation=(-30°, +30°)`, `p_scaling=0`, `bg_style_seg_sampling=False`, `border_mode_seg='constant'`, `padding_value_seg=-1`). Apply it to label-only input. Measure, per class and stratified by local vessel diameter: retained label volume, retained skeleton length, and change in connected-component count.

If ±30° rotation erodes >5 % of the label volume on 1–2 mm branches, or breaks skeleton continuity, the rotation ablation's outcome is largely predicted and the paired training run may be unnecessary. If it erodes ~nothing, the interpolation half of the dispute closes on paper and the ablation shrinks to the orientation question alone — where ImageCAS's measurement, for all its flaws, already points one way. **Either result removes or shrinks a scheduled GPU experiment.** Run it before the rotation ablation.

The same harness answers the second half of the question nobody asked: **why does TotalSegmentator use `nnUNetTrainer_DASegOrd0_NoMirroring` for its coronary task?** The mirroring note quotes that trainer name verbatim (`:61–62`) and reads only the `NoMirroring` half of it. `DASegOrd0` is the half that changes **augmentation-time label interpolation**: `nnUNetTrainerDAOrd0.py:57` adds `mode_seg='nearest'` to `SpatialTransform`, which nnU-Net's default omits (so the default is `mode_seg='bilinear'`, batchgeneratorsv2 `spatial.py:32`, taking the one-hot-plus-argmax path). The most-used nnU-Net-based CT model in the world changed exactly this setting for exactly this anatomy, and the vault cites the file without asking why. That is a free, directly relevant piece of engineering evidence, and the harness above measures which of the two is kinder to a 3-voxel tube.

### (2) The taper rule silently sets the CT normalisation window

`Proposed changes…md:198–200` leaves the taper rule open ("Pick one — diameter < 1.0 mm, visibility, or follow-the-centerline — and calibrate on 5–10 cases"). Nobody notices that this choice **moves the intensity window**. The fingerprint's foreground is `seg > 0`, so a more generous taper adds thin, heavily partial-volumed, low-HU distal voxels to the foreground, which lowers `percentile_00_5` and widens the clip window; a conservative taper narrows it. So an annotation-protocol decision, taken for anatomical reasons, silently changes how every voxel of every image is normalised — and changes it differently between the binary and multiclass tasks if their masks differ in extent.

Two consequences worth recording: the taper-rule calibration on 5–10 cases should report the resulting foreground HU percentiles, not only the anatomical stopping point; and if 710 and 711 come out with materially different windows, that is the same effect showing up between two label sets on identical images, which makes it measurable immediately.

### (3) Which CCTA failure modes actually matter for this objective — the vault has imported three from a problem it is not solving

The project labels *which vessel*, not *whether there is a stenosis*. Sorting the confounders note by that objective:

| Confounder | In scope? | Why, and what to do instead |
|---|---|---|
| **Calcium blooming** | **Yes, reframed** | It does not confuse LAD with LCx. It matters through **continuity**: a bloomed severe lesion can break the segment distal to it, and a dropped or fragmented distal segment is a *branch-detection* failure — the project's headline metric. So the relevant observables are branch detection rate, Betti-0 and clDice on the segment distal to a calcified lesion, **not** boundary Dice. The action is **stratified evaluation** by disease status (ImageCAS-X reports 388 diseased / 412 not), not an augmentation. |
| **Calcium-blooming simulation as augmentation** | **No** | The simulator is real and the physics is characterised, but no one has trained a segmenter with it; wiring a CT simulation chain into nnU-Net's dataloader is a project, and the benefit is unmeasured. The note already says this (`:143–149`) and `Proposed changes…md:433` records it correctly. It should stay a recorded research direction and appear on **no** experiment list. |
| **Stents** | **No — and the cohort argues it closed, not unreachable** | Three reasons. (i) The naming task is unchanged by a stent: a stented mid-LAD is still LAD. (ii) No augmentation can create one, as the note concedes. (iii) **ImageCAS's own inclusion criteria make stents rare by construction** — arXiv:2211.01607v2 §3: *"For those patients who have previously been diagnosed with coronary artery disease, early revascularization (within 90 days after) are included"*, i.e. these are pre-revascularisation diagnostic scans. The stent-prevalence question in `Proposed changes…md:432` is still worth one metadata check, but the prior is low. **Do not hand-fetch the AJR editorial (403).** The "<3 mm stent lumen" claim is about in-stent restenosis *grading*, which this project does not do. It should be struck from §5 rather than chased — that is one fewer paywall to fight. |
| **Motion** | **Yes, and it matters for naming too** | The note's segment-specific finding (mid RCA, mid LAD, distal LAD) is the most directly actionable fact in the whole slice, because a motion-smeared distal LAD is exactly where continuity breaks and a fragment gets dropped or misnamed. `Proposed changes…md:328` already adds the subgroup breakdown — keep it. **Extension:** motion also degrades *label* quality, so the same three segments should be pre-registered as the ones to inspect in the annotation overlap set. If inter-annotator agreement drops there, the model's per-class ceiling is lower there, and the acceptance thresholds in §2.4 need a per-segment adjustment rather than a per-class one. Nobody has connected the motion evidence to the annotation protocol. |
| **TW-MoCoNet / motion correction** | **No** | Verified, correctly reasoned in the note (`:113–115`): it is an input-domain correction applied upstream of anything this project controls. Interesting, decision-irrelevant. |
| **Low-dose noise** | **No — retire the section** | The confounders note (`:117–128`) and the table row hedge extensively about a risk this cohort does not have. arXiv:2211.01607v2 §3, verbatim: *"The high-dose CTA is performed"*. Single protocol, high dose, one scanner. The section can be deleted, which removes a "flagged as a gap" that is not a gap. |

So: **blooming and motion survive, both reframed from image-quality problems into continuity-and-evaluation problems; blooming-simulation, stents and low-dose are imported from a stenosis-assessment problem and should come off the list.** Net effect: two entries removed from §5's not-evidenced table, one paywalled source no longer worth chasing, and no augmentation change.

### (4) Mirroring and the binary model: the chirality argument does not apply, but a better argument does

The chirality argument (`Mirroring…md:29–38`) is correct and well made — a flip along *any* single axis is orientation-reversing, so `onlyMirror01` is not a partial fix, and I verified the trainer it names exists and does what the note says (`nnUNetTrainerNoMirroring.py:38–52`, `mirror_axes = (0, 1)` for 3D). But note that the argument is about **labels**: it says no permutation of class names makes a mirrored volume correct. A binary model has no lateralised labels, so **the argument does not transfer**, and the note says so (`:114–115`).

What remains for the binary model is a weaker and different claim: mirroring feeds the network anatomy off the manifold of real patients. That is a **regularisation trade-off, not a correctness bug** — and nnU-Net trains with mirroring on chiral anatomy across every MSD task, usually to benefit. So the note's conclusion ("legitimately an empirical choice", `:114–118`) is right.

**But there is a project-specific reason to default the binary run to no-mirror that the vault does not give, and it is stronger than the empirical one:** §3.4 promotes **binary-init fine-tuning to priority 1**. A binary encoder trained with `mirror_axes = (0,1,2)` has been explicitly trained to be *invariant to handedness* — it has been taught to discard the single cue the multiclass task depends on to tell the left system from the right. Mirroring in the binary stage is therefore a **transfer liability**, not just an empirical toss-up, and the liability lands on the experiment the proposals rank first. That it also happens to be the direction the one cohort-specific measurement points (ImageCAS's 2.63/2.73 %) is a bonus, not the argument.

**Recommendation:** default **both** stages to no-mirror, on transfer grounds for the binary stage and correctness grounds for the multiclass stage. Keep the {default, no-mirror} arm of the cheap ablation, but reframe its purpose: it records *what mirroring was worth on the binary task*, it does not decide multiclass policy — that is decided by the chirality argument and is not empirical. This is a cleaner justification than "fold it into the same cheap ablation rather than assuming the default" (`Mirroring…md:116–118`), which leaves the default in place until measured.

### (5) TTA: affordable, but there is nothing left to afford

Reconciling with §2 of the plan ("~3–4× more sliding windows at inference", `Training plan.md:67`):

**Window count, from source.** `compute_steps_for_sliding_window` (`sliding_window_prediction.py:39`): `num_steps = ceil((image − patch) / (patch·tile_step_size)) + 1`.
- No crop, ~256³ patch, 512×512×~240 volume, step 0.5: 3 × 3 × 1 = **9 windows**.
- Heart-cropped, ~300×300×240: 2 × 2 × 1 = **4 windows**.
- So dropping the crop costs **~2.25×** here, not 3–4×. The plan's 3–4× is the *volume* ratio (512²/300² ≈ 2.9), which is what the window count approaches as the patch shrinks. With the plan's large patch the penalty is smaller than the plan claims — a point in the plan's favour that it does not make.

**TTA multiplier, from source.** `_internal_maybe_mirror_and_predict` (`predict_from_raw_data.py:574–590`): one forward pass plus one per non-empty subset of `mirror_axes`. For `(0,1,2)`: **8×**. Mirroring is the *only* TTA nnU-Net implements.

**Cost per case.** 9 windows × 8 = 72 forward passes of a ~256³ patch. On an H100 in autocast, a 256³ nnU-Net `3d_fullres` forward is order 0.2–0.6 s (estimate, not measured — 8× the voxels of a 128³ patch), so ~15–45 s GPU per case with TTA against ~2–5 s without. Over ImageCAS's 250-case official test set: **~1–3 GPU-hours with TTA, ~10–20 min without.** Over 1000 cases: ~4–12 GPU-hours. Not 40–125. Per-case CPU preprocessing and export on a 512²×240 volume is order 30–90 s and will often dominate wall-clock anyway, and it parallelises across workers.

**Verdict: TTA is affordable — it is a rounding error against a 3 × 23:50 h training chain.** The vault's conclusion is right and its arithmetic is not.

**And disabling mirroring removes all of TTA's value, not most of it.** Because mirroring *is* nnU-Net's TTA, the day the multiclass model runs `NoMirroring`, `use_mirroring=True` in `src/segtrain/evaluate.py:56` becomes a no-op — exactly as the mirroring note correctly observes (`:85–86`). There is no scaling TTA, no rotation TTA, no hook. So:
- For the **multiclass** model, TTA is not a lever, not an experiment, and not a cost. It disappears.
- For the **binary** model, if mirroring stays on, TTA comes free with the default predictor and there is no decision to make; if mirroring goes off per §4/(4) above, TTA disappears there too.
- The lever that *does* remain, for both, is **`tile_step_size`** — a pure inference argument requiring no retraining. Sweeping it (0.5 → 0.25 → 0.1, costing 9 → ~25 → 121 windows) on one fold's predictions is a post-hoc, GPU-cheap, fully reversible experiment, and it is the one that directly addresses the fragmentation lever §3.4 cares about.

**Fix:** in §3.4 priority 6, delete "TTA" and keep "sliding-window overlap sweep", noting it needs no retraining. In §3.1 keep the "confirm overlap is 50 %" gate — it is correct (`tile_step_size=0.5` at `evaluate.py:52` and `nnUNetTrainer.py:1272`) — and upgrade it from **[reported]** to **[source]**.

### (6) Two smaller extensions

- **Nothing gates the trainer, only the planner.** All four proposed pre-submission gates read planner output. Two of the most consequential facts are only in the **trainer log**: `do_dummy_2d_data_aug` (`nnUNetTrainer.py:512`) and, if a line is added, `mirror_axes`. Since the repo already instruments the trainer with `EventWriter` and `on_train_start` already emits `patch_size`, `batch_size` and `spacing` (`nnUNetTrainer_segtrain.py:174–187`), the cheapest fix is to add `mirror_axes` and `do_dummy_2d_data_aug` to that `run_start` event. Then the gate is a one-line check against `events.jsonl` instead of log-scraping, and it is checkable *after* the first epoch rather than never.
- **ASOCA's anisotropy should be checked before §3.3 is run.** External validation on ASOCA means running inference on 0.625 mm-slice data with a model whose plans were fit to 0.25–0.45 mm. Preprocessing for inference resamples each case to the plans' target spacing, and `determine_do_sep_z_and_axis` triggers per case on `max/min > 3`: at 0.625 mm slices with ~0.3–0.4 mm in-plane the ratio is ~1.6–2.1, under the threshold, so separate-z will not fire. But the resampling factor in z is ~1.8×, done with order-3 upsampling of the image — an 80 % z-interpolation of a dataset the model never saw. That is a confound the predicted "5–8 Dice-point drop" (`Proposed changes…md:335`) does not separate from genuine domain shift, and it should be reported alongside the drop. Cheap: report each ASOCA case's native spacing and its resampling factor.
